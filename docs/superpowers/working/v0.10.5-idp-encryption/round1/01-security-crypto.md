# Round 1 review — Security / Cryptography

**Reviewer lens**: AES-GCM envelope encryption, key handling, attack surface
**Spec under review**: docs/superpowers/specs/2026-05-17-idp-token-encryption-design.md
**Overall verdict**: SOUND-WITH-IMPROVEMENTS

The core construction (per-row 32-byte DEK, fresh 12-byte random nonces for both wrap and data, GCM tags retained, length-prefixed concatenation with fixed offsets) is cryptographically sound. The nonces are random per encrypt call and there is no key reuse beyond the master key, where birthday risk is negligible for the expected volume (≤ ~10^8 wraps before approaching 2^32 random-nonce concern, well above realistic user count). However, there are several real issues around AAD/context binding, the plaintext fallback semantics, the backward-compat sentinel, key material handling, error leakage, and CLI/key-loading surfaces that should be addressed before this ships.

## Concerns

### 1. `EncryptionContext` is accepted but never bound as AAD — MAJOR
**Description**: Both `encrypt()` and `decrypt()` take an `EncryptionContext` (`{ org_id, column }`) and the spec explicitly states callers always pass it, but the parameter is `_context` (unused) in the implementation. AES-GCM supports AAD via `cipher.setAAD(...)` precisely for this purpose. Without AAD binding, an attacker with DB write access can swap a victim's `idp_access_token` ciphertext into the attacker's row, or swap an `idp_refresh_token` cell into the `idp_access_token` cell of the same row, or copy an old (rotated/revoked) ciphertext back into place — all of these decrypt cleanly because the ciphertext is not bound to "this user, this column". This is a real attack against insider-with-DB-write and against backup-restore-rollback scenarios.
**Recommendation**: Bind context as AAD on the data layer: `cipherData.setAAD(Buffer.from(\`${context.org_id}|${context.column}|${user_id}\`, "utf8"))` and mirror on decrypt. Include `user_id` (the row identity) — not just `org_id`/`column` — because the attack of interest is cross-row swap within the same org+column. Document the AAD format as part of the `v1` wire format so a future `v2` can evolve it. Without `user_id` in AAD, the spec gains little defense beyond column-swap protection.

### 2. Backward-compat plaintext passthrough on decrypt is a silent downgrade — MAJOR
**Description**: `decrypt()` returns `ciphertext` unchanged when the `enc:v1:` prefix is absent. Combined with the lazy-migration story, this means an attacker who can write to the DB (or restore an old backup) can overwrite an encrypted row with arbitrary plaintext and the daemon will happily accept it as the user's IdP token. The daemon cannot distinguish "legitimate pre-encryption row" from "attacker-supplied plaintext token". Even worse, after `migrate-idp-tokens` has run, there is no flag that says "from this point forward, plaintext is forbidden" — the code path is permanently lenient. This converts a confidentiality control into one that an active attacker can downgrade by overwriting.
**Recommendation**: After the migration step, encryption should be enforced strictly. Add an env var `COORDINATOR_ENCRYPTION_STRICT=1` (or auto-detect post-migration via a `meta` table flag set by `migrate-idp-tokens`) that makes a non-`enc:v1:` value on read an error rather than a passthrough. At minimum, log a high-severity warning on every plaintext-passthrough decrypt after encryption is enabled, with row identifier, so operators detect tampering or stale rows. Document that strict mode is the intended steady-state.

### 3. `enc:v1:` prefix is forgeable — MAJOR
**Description**: The prefix is a content marker, not a cryptographic signal. An attacker who can write a row can choose between "looks like plaintext" (downgrade attack, concern #2) and "looks like ciphertext but is garbage" (forces the user into the decrypt-error → re-auth flow, which is a denial-of-service / forced re-authentication vector). Also, an attacker who flips one byte of a real ciphertext triggers the same re-auth flow — every encrypted row is fragile to single-byte corruption, and the error handling makes this a user-visible logout. There is no integrity layer above the row that would distinguish "we wrote this" from "someone else wrote this".
**Recommendation**: Two improvements: (a) bind row identity via AAD (concern #1) so cross-row tampering fails noisily and predictably, and (b) consider rate-limiting forced re-auth flows triggered by decrypt failure per user to mitigate the DoS angle. The fundamental forgeability of the prefix is acceptable as long as #1 and #2 are addressed; the prefix is just a routing hint, not an authentication tag.

### 4. Master key accepts both hex AND base64 — format ambiguity — MAJOR
**Description**: `decodeKey()` accepts "either 64 hex chars or base64-encoded 32 bytes". A 64-character string can be valid in both encodings simultaneously (every hex char is a valid base64 char). Auto-detection in `decodeKey` (not shown in spec but implied) will pick one interpretation; the operator may believe they set the other. The two interpretations yield completely different 32-byte keys, so the operator runs encrypted-looking code with a key they didn't intend, and all decrypts fail when they later "correctly" supply the key. Silent key misinterpretation is a class of bug that loses data.
**Recommendation**: Require an explicit scheme prefix: `hex:<64hexchars>` or `base64:<...>`. Reject ambiguous inputs. Or pick one (base64 — matches `openssl rand -base64 32` in the docs) and reject the other. Also reject keys with low entropy (e.g., all-zeros, ASCII printable patterns) — a 32-byte all-zero key currently passes the length check.

### 5. No master key strength / source quality validation — MAJOR
**Description**: The only validation is `key.length !== 32`. An operator can set `COORDINATOR_ENCRYPTION_KEY=$(echo -n "passwordpasswordpasswordpassword" | base64)` and the system accepts it. A 32-byte key derived from a low-entropy passphrase is brute-forceable. The spec does not provide a KDF (Argon2/scrypt) for password-derived keys, but it also doesn't warn against passphrase use. Operators will use passphrases.
**Recommendation**: (a) Document explicitly that the value MUST be cryptographically random and provide the exact command (already there). (b) Add a soft entropy heuristic at load time — reject keys where Shannon entropy < ~4.5 bits/byte and log a clear error "this looks like a passphrase, not a random key. Use `openssl rand -base64 32`." (c) Or support a separate `COORDINATOR_ENCRYPTION_PASSPHRASE` env var that goes through Argon2id with a stored salt. Don't conflate the two paths in one env var.

### 6. No key zeroization; master key persists in process memory and Buffers — MINOR
**Description**: `EnvVarMasterKeyProvider.load()` reads from `process.env`, which keeps the original string in the V8 heap indefinitely (V8 interns env strings; `delete process.env.X` does not zero the memory). The decoded `Buffer` is held by reference on `EnvelopeEncryption` for daemon lifetime, and intermediate DEKs are never zeroed after use. A process memory dump (acknowledged out of scope but worth defending) recovers the master key trivially. The spec lists this as "out of scope" but provides no mitigations at all.
**Recommendation**: (a) Read the env var into a Buffer, then `delete process.env.COORDINATOR_ENCRYPTION_KEY` immediately after load — at least removes one copy. (b) Allocate the master key Buffer with `Buffer.allocUnsafeSlow(32)` so it lives off the shared pool and can be wiped on shutdown. (c) After each encrypt/decrypt, `dek.fill(0)` before the variable goes out of scope. None of these defeat a determined memory-dump attacker but they reduce the window meaningfully.

### 7. `hmac()` uses the master key directly as the HMAC key — MAJOR
**Description**: The `hmac()` method does `createHmac("sha256", this.masterKey)`. Using the same key for two cryptographic purposes (AES-GCM encryption of DEKs AND HMAC-SHA256) violates key separation. Even though the spec says "not used for IdP tokens; required by interface contract", the method is callable and will be called by future code. An HMAC oracle on the master key can leak partial information about it under specific scenarios and definitely makes the master key cross-purpose.
**Recommendation**: Derive a separate HMAC subkey: `const hmacKey = hkdfSync("sha256", this.masterKey, Buffer.alloc(0), Buffer.from("mcp-coordinator/hmac/v1"), 32)`. Same pattern (HKDF with distinct info) for any future per-purpose subkey. Document that the master key MUST NEVER be used directly — only through HKDF-derived purpose-specific subkeys.

### 8. Decrypt error message and logging leak structure — MINOR
**Description**: Spec says "decrypt error … is logged at ERROR level with the user id". This is good for operators but means anyone with log access learns which users had tamper events. Combined with the forced re-auth flow, an attacker who flips one byte in a single user's row triggers an ERROR log naming that user and forces them through re-login — a targeting primitive. Additionally, the `verify-encryption-key` CLI prints "FAIL: master key cannot decrypt existing rows. Wrong key?" — does not leak the key but does confirm "encrypted rows exist" to anyone who can run the CLI.
**Recommendation**: Log a hash/prefix of the user id rather than the full id (still useful for correlation, less useful for targeting). Make decrypt errors generic from the caller's perspective — never propagate the underlying GCM "Unsupported state or unable to authenticate data" through to any API surface. Constant-time the decrypt path so timing doesn't reveal "wrong DEK wrap" vs "wrong data tag" vs "bad base64".

### 9. CLI `--rotate --new-key=<...>` puts a key on the command line — MAJOR (when implemented)
**Description**: Spec defers rotation to v0.10.6 but lists `migrate-idp-tokens --rotate --new-key=<...>` as the planned flag. Keys on the command line appear in `ps`, shell history, journald, and PID 1's `/proc/<pid>/cmdline`. This is a well-known footgun.
**Recommendation**: When implemented, accept the new key only via env var (e.g., `COORDINATOR_NEW_ENCRYPTION_KEY`) or stdin (`--new-key-stdin`), never on argv. Document this constraint in the v0.10.5 spec so the v0.10.6 implementation doesn't repeat it.

### 10. No audit log of crypto operations or key load — MINOR
**Description**: Spec mentions one boot warning (when key is unset) and decrypt-error ERROR logs. There is no INFO/AUDIT log on successful key load ("encryption enabled, key fingerprint=<sha256(key)[:8]>"), no record of how many decrypts/encrypts happened, no record of `migrate-idp-tokens` runs in any DB-backed audit table. After-the-fact incident response will struggle to answer "when did encryption get turned on? Was the right key in place during window X?".
**Recommendation**: At boot, log `{ event: "encryption_enabled", key_fingerprint: sha256(masterKey).slice(0,8).toString("hex") }` — fingerprint lets operators confirm "same key as yesterday" without exposing the key. Write `migrate-idp-tokens` start/end + counts to `audit_log` with a non-secret summary. Periodically log rolling counts of encrypt/decrypt/decrypt-fail.

### 11. Concurrent key load race on boot is undefined — MINOR
**Description**: `load()` is `async`, called once at boot per the comment. But the boot wiring shows `await new EnvVarMasterKeyProvider().load()` inline — there is no singleton, no lock. If two code paths construct providers (e.g., a worker thread, a CLI subcommand invoked while daemon is running, a hot-reload scenario), each reads `process.env` independently. Not a confidentiality bug today, but the interface implies "called once" without enforcing it.
**Recommendation**: Make `EnvVarMasterKeyProvider` a memoized singleton (cache the Buffer on first load) and make the cached Buffer the canonical reference passed to all consumers. Forbid (or just don't construct) multiple `EnvelopeEncryption` instances per process.

### 12. `migrate-idp-tokens` reads then writes plaintext through the daemon — MINOR
**Description**: The migration reads plaintext rows and re-encrypts them. During migration, plaintext tokens are pulled into application memory in batches of 100. Fine in steady state, but if the migration crashes mid-batch and the operator inspects logs or a crash dump, the in-memory tokens of the failed batch are recoverable. Less critical than the master-key memory exposure but worth noting.
**Recommendation**: Wrap the migration batch loop in a `try { ... } finally { batch.forEach(r => zero(r.idp_access_token); zero(r.idp_refresh_token)) }`. Don't include row contents in any log line (the spec already says "logs progress every 1k users" — confirm that means counts only, not values).

### 13. No nonce-reuse protection beyond `randomBytes(12)` quality — NIT/MINOR
**Description**: AES-GCM catastrophically loses confidentiality (and authenticity!) under nonce reuse with the same key. Random 96-bit nonces have a collision probability of ~2^-32 at 2^32 messages — fine for IdP tokens at realistic scale, but the master key is used to wrap every DEK ever generated, across daemon restarts and across the entire fleet of deployments sharing a key. If an operator copies the same key across many instances (the v0.10.5 model has no per-instance subkey), the combined wrap-nonce space across the fleet shrinks the safety margin. Still very safe, but worth a deliberate design note.
**Recommendation**: Either (a) add a deterministic nonce-misuse-resistant mode for the wrap layer (AES-GCM-SIV is the standard answer, available via libraries), or (b) document the operational bound explicitly: "this design is safe up to ~2^32 total DEK wraps across all instances sharing the master key; rotate the master key before this point". Realistically, (b) is enough — IdP token writes don't happen at that scale.

### 14. `verify-encryption-key` produces a chosen-ciphertext oracle (weak) — NIT
**Description**: The CLI lets anyone with shell access submit the env-var key and learn pass/fail against one real ciphertext. Combined with #4 (format ambiguity), an operator confused about hex vs base64 can iterate keys against the CLI. Not exploitable remotely and not a real attacker primitive against well-handled keys, but worth noting.
**Recommendation**: Acceptable as-is; the CLI requires local shell access which is already a higher trust level than DB-read. Optionally rate-limit `verify-encryption-key` invocations (sleep on fail) to prevent shell-script brute-force in a constrained scenario.

### 15. No protection against key-version downgrade — MINOR
**Description**: Once `enc:v2:` ships in the future, an attacker with write access can replace a `v2` ciphertext with a `v1` ciphertext they generate against the same master key (if it's reused) or against the old key if it lingers in env. The `decrypt()` dispatcher must refuse old versions once an upgrade is complete.
**Recommendation**: Add a per-deployment "minimum acceptable version" config knob now (defaults to `v1`). When `v2` ships, operators set `COORDINATOR_ENCRYPTION_MIN_VERSION=v2` after re-encrypting and `v1` rows are then rejected on read. Documenting this slot now is cheap; retrofitting it later is much harder.
