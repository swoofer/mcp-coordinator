# Plan Round 1 — Acceptance + tests (v0.10.6)

**Verdict**: NEEDS-TIGHTENING

Plan is well-structured with strong test coverage in most areas (T04 validator matrix, T13 last-admin matrix, T08 CSP/ACAO matrix are exemplary). However, the acceptance criteria leak judgment in several places ("lint clean" with no lint script, "no flakes on N reruns" with no enforcement, manual smoke for visual CSS), the coverage-gate mechanism (vitest.config.ts per-file thresholds) is never bound to the new files, and several R1+R2 bug classes (per-IP RL pre-auth pathway, TOCTOU under single-connection SQLite, CSP/ACAO header presence assertion mechanics, 409 ORG_NAME_TAKEN error-code mapping from SQLITE_CONSTRAINT_UNIQUE) lack mutation-resistant tests with a concrete setup recipe.

## Findings

### 1. T01 / T02 / T05 / T06 / T08 / T09 / T11 / T12 / T13 / T14 (acceptance verbiage): "Lint clean" is undefined
**Issue**: 9 tasks list "Lint clean" as an acceptance bullet. `package.json` has no `lint` script (verified: only `build`, `test`, `test:watch`, `test:e2e`, `cli`, `start`, `dev`, `dev:stdio`, `perf:*`, `chaos:*`, `prepublishOnly`). An implementer cannot tell when this is satisfied; it becomes judgment.
**Recommendation**: Globally replace "Lint clean" with the exact command pair: `npx tsc --noEmit` passes AND (where introduced) the admin-specific grep lints in T09 (`scripts.lint:admin`) pass with exit code 0. T09 must wire `lint:admin` into `prepublishOnly` so the grep checks are enforced on release. Without this, T09 ships dead lint scripts.

### 2. T01 / T03 / T04: Coverage gate is never added to `vitest.config.ts`
**Issue**: `vitest.config.ts` enforces 100% per-file thresholds for every security-critical file by explicit entry. Plan never adds entries for `src/admin/validate.ts` (T04: "100% coverage on src/admin/validate.ts — small file, easy gate"), `src/admin/handle-admin-orgs.ts` (T05), `src/admin/handle-admin-users.ts` (T06), or the `csrf.ts` re-export site (T01). Per-file 100% is meaningless unless declared in the config. T13 acceptance says "no per-file 100% threshold per V2 Cut#6" — but that conflicts with the project-wide enforcement pattern.
**Recommendation**: Either (a) explicitly add `vitest.config.ts` threshold entries for `src/admin/validate.ts` 100%, and `handle-admin-orgs.ts`/`handle-admin-users.ts` at branches: 90 (handlers have hard-to-cover error paths like SQLITE_BUSY) as part of T05/T06 acceptance — making coverage gate enforceable in CI; or (b) explicitly document in the plan that admin handlers are exempt with a reason. Currently neither.

### 3. T13 (Per-IP rate limit test): Test recipe missing for pre-auth path
**Issue**: T13 says "61st POST from same IP in 60s → 429 + `Retry-After`" but does not specify: (a) how to inject IP into vitest integration test (better-sqlite3 + node test server bind to 127.0.0.1 — all requests look identical), (b) whether to mock `ctx.rateLimiter.check` or drive the real limiter, (c) how to reset the limiter between tests (sticky state across `100 GETs` then `61 POSTs` cases). Also V3 PATCH 4 says RL is inside handlers (post-auth), but the test verifies pre-auth IP allowlist. If "per-IP" means `req.socket.remoteAddress` it's always 127.0.0.1 in tests → loop hits the same bucket → reliable. But if it uses `X-Forwarded-For`, the test needs explicit headers.
**Recommendation**: Add concrete setup: `for (let i = 0; i < 61; i++) await fetchClient.post("/api/admin/orgs", validBody);` with `expect(responses[60].status).toBe(429)`. Specify the IP key source explicitly (`req.socket.remoteAddress` per current rate-limit pattern → all 127.0.0.1 → naturally same bucket). Use `vi.useFakeTimers()` to control the 60s window OR add a `coordinator.rateLimiter.reset()` helper called in `beforeEach`. Also: assert `Retry-After: <number>` numeric and `body.message` does NOT leak request count.

### 4. T13 (Last-admin TOCTOU "2 concurrent demotes" test): Better-sqlite3 is synchronous — test as written is not concurrent
**Issue**: T13 says: "2 concurrent demotes against last 2 admins → exactly one 200 + one 409 (V3 PATCH 5: under single-connection better-sqlite3, second blocks then sees post-commit state)." But better-sqlite3 is synchronous and uses one connection — there is no concurrency to race. `Promise.all([demoteA(), demoteB()])` resolves serially. The test cannot exercise actual TOCTOU; the 2-clause guard SQL (V3 PATCH 1) is what protects against the race, and the guard executes inside one `.immediate()` tx → no race window exists.
**Recommendation**: Rephrase test as: "sequential demotes of last 2 admins → first 200, second 409 CONFLICT_LAST_ADMIN (proves guard SQL holds invariant across handler calls)." Drop "concurrent" language. Add a separate sentinel test: "monkey-patch the SQL builder for V2's 3-clause variant (or temporarily install the buggy SQL) → second demote returns 200 → test FAILS, proving the 2-clause guard is the protector." Without this differential test, you cannot prove the 2-clause guard is correct vs the 3-clause buggy one — the "dead-clause repro" test only proves correct behavior given current SQL, not that 2-clause vs 3-clause is the load-bearing change.

### 5. T08 (CSP header test): Mechanics not specified
**Issue**: T08 says "GET `/dashboard/admin.html` → response headers include `Content-Security-Policy` (value matches V2)". But the CSP value is long (8+ directives). String-equality is brittle (whitespace, directive order); substring-match misses mutations (an attacker / regression that drops `script-src 'self'` would still pass `expect(header).toContain("default-src 'none'")`).
**Recommendation**: Parse the CSP into a directive map (`split(/;\s*/).map(d => d.trim().split(/\s+/))`) and assert each of the 8 directives is present with exact source list: `expect(parsed['script-src']).toEqual(["'self'"])`, `expect(parsed['default-src']).toEqual(["'none'"])`, etc. This catches single-directive mutations. Also assert `parsed['script-src']` does NOT contain `'unsafe-inline'` or `'unsafe-eval'` (mutation-resistance against future "quick fix" PRs that loosen CSP).

### 6. T08 (ACAO drop test): Negative assertion correctness
**Issue**: T08 says `/dashboard/admin.html` → "Does NOT include `Access-Control-Allow-Origin`". This catches the regression today, but doesn't test the boundary precisely: what if the regex matches `admin.html` but the existing handler still emits ACAO unconditionally elsewhere? Need to verify ACAO is dropped specifically by the `isAdminPage` branch, not by accidental ordering.
**Recommendation**: Add: (a) `expect(res.headers['access-control-allow-origin']).toBeUndefined()` for each admin page; (b) `expect(res.headers['access-control-allow-origin']).toBe('*')` for `/dashboard/index.html` (proves the else-branch still runs); (c) Add a test for `/dashboard/admin.html?return_to=foo` (query string variant in V3 PATCH 7 regex) confirming admin-branch is taken; (d) Add `/dashboard/Admin.html` (case sensitivity) — the regex is case-sensitive → ACAO present → confirms regex doesn't over-match. This 4-vector matrix mutation-resists the regex.

### 7. T05 (409 ORG_NAME_TAKEN test): SQLITE_CONSTRAINT_UNIQUE error-code surfacing not tested
**Issue**: T13 says "409 ORG_NAME_TAKEN on duplicate name (relies on T03 UNIQUE INDEX)." But the implementation catches a thrown better-sqlite3 error and maps it to 409. The mapping recipe is: `if (err.code === 'SQLITE_CONSTRAINT_UNIQUE' && err.message.includes('orgs.name'))`. If the code uses just `SQLITE_CONSTRAINT` (broader), a future UNIQUE on another column would also surface as ORG_NAME_TAKEN. Test as currently scoped only proves "happy 409 path" — not the discriminator.
**Recommendation**: Add 2 tests: (a) insert duplicate name → 409 ORG_NAME_TAKEN with `body.code === 'ORG_NAME_TAKEN'` and `body.message === 'Org name already exists'` (no echo of attempted name per V3 PATCH 11); (b) if/when a second UNIQUE constraint exists (e.g., users.email), seed a conflict on that table during a PATCH path — assert it does NOT return ORG_NAME_TAKEN (proves the discriminator is column-specific). If no second UNIQUE exists, document in T05 acceptance that error-mapping must inspect both `err.code === 'SQLITE_CONSTRAINT_UNIQUE'` AND `err.message.includes('idx_orgs_name')` or `'orgs.name'`.

### 8. T13 (Audit-emission invariants): Tx atomicity not mutation-tested
**Issue**: T13 says "Mutation+audit in one tx: simulate INSERT failure (mock prepare to throw) → no audit row." This is good but only tests one failure mode. The acceptance for T05/T06 says "All `db.transaction()` end with `.immediate()`" — but the test never inverts this: if someone removes `.immediate()`, the handler still functions correctly for non-concurrent test loads. The `.immediate()` choice is a concurrency-safety property, not a functional one — current tests cannot detect its removal.
**Recommendation**: Add a static assertion test: `tests/unit/admin-tx-immediate.test.ts` greps source for `db.transaction(` and asserts every match is followed by `.immediate()` within ~50 chars (regex: `/db\.transaction\([^)]+\)\.immediate\(\)/`). Mirrors the inline-JS lint pattern in T09. Without this, the V3 PATCH 2 invariant is lint-only and can silently regress.

### 9. T13 / T14 (Test overlap): Last-admin server-side 409 covered in both
**Issue**: T13 covers "PATCH on last admin → 409 CONFLICT_LAST_ADMIN" exhaustively. T14 covers "Bypass disabled UI via direct fetch in browser console. Assert 409 CONFLICT_SELF_DEMOTION" — same backend behavior tested twice (once via fetch, once via Playwright `page.evaluate(() => fetch(...))`). The e2e test adds ~0 unique coverage over the integration test for the 409 path; the UI revert behavior is the e2e's actual job.
**Recommendation**: Reframe T14's "bypass disabled UI" test as: "Programmatically enable the disabled `<option value=member>` via `option.disabled = false`, set it via the dropdown, click Save → observe inline error rendered + dropdown reverts to 'admin' + toast NOT shown." This tests UI revert/error-render behavior that T13 cannot test. Drop the redundant 409 status assertion (or keep as 1-liner).

### 10. T14 (Playwright e2e): Browser matrix + CI integration absent
**Issue**: T14 acceptance says "All e2e tests pass on local + CI" + "No flakes on 5 reruns" but does not specify: (a) browser matrix (chromium/firefox/webkit — Playwright defaults to all 3, costs CI minutes), (b) which `playwright.config.ts` projects run in CI vs local, (c) fixture reuse (mention `tests/e2e/helpers/coordinator-fixture.ts` exists but no verification it supports multi-context for the "concurrent rename" test), (d) flake-detection mechanism ("no flakes on 5 reruns" is unenforceable — CI runs once per PR). axe-core devDep is "POSSIBLY MODIFIED" — non-decision.
**Recommendation**: Spell out: (a) CI runs chromium-only on PR, full matrix on main merge (or document current pattern); (b) verify `coordinator-fixture.ts` exposes a `newAdminContext()` or document the gap; (c) add `--retries=2` to playwright.config.ts CI mode and assert in T14 acceptance that no test relies on retry to pass (Playwright reports flaky-but-passed); (d) make axe-core decisive: "add `axe-playwright@^2` as devDep — already needed." (e) For concurrent-rename test, document that it requires 2 BrowserContexts with distinct cookies/sessions — verify the test helper supports this or add as a sub-task.

### 11. T09 (jsdom unit tests): Test infrastructure dependency unresolved
**Issue**: T09 open question 4 says "do we already have a jsdom test runner configured?" and "if not, the setup overhead may not justify the small test surface." Open question is in the plan, not resolved. T09 acceptance includes "jsdom tests pass" — but if jsdom isn't installed, this acceptance is uncheckable. Vitest devDep verified but `jsdom` is not in `devDependencies` (verified: only `msw`, `fast-check`, etc.).
**Recommendation**: Resolve before merge. Add `jsdom` (or `happy-dom` — smaller) to T09's `package.json` modifications. Add `vitest.config.ts` test env override for `tests/unit/admin-js-shared.test.ts` (likely `// @vitest-environment jsdom` pragma in the test file). Verify the test runner picks up the env. Without this, the jsdom tests fail to even discover the DOM globals.

### 12. T13 / T14 (Integration vs unit boundary): `tests/helpers/admin-session.ts` only mints session — needs more
**Issue**: The cross-cutting "Test infrastructure" section creates `adminFetchClient` but the integration tests at T13 also need: (a) a way to seed orgs/users with specific role distributions for last-admin matrix (requires direct DB access alongside the HTTP client), (b) a way to roll back state between tests (cheap recreate vs sweeper), (c) a way to mint a *member* session (for the 403 test) — the helper signature accepts `role` but mintSession's pattern is not documented. T13 says "Use existing CSRF cookie helper from auth tests" — but `adminFetchClient` already wraps CSRF; double-spec.
**Recommendation**: Lift `tests/helpers/admin-session.ts` creation out of T13 into Phase A as T03b (~30 LOC). Specify: (a) exports `adminFetchClient(coord, { role, userId? })`, (b) returns `{ fetch, csrfToken, sessionCookie, userId }` for tests that need raw access, (c) exposes `coord.db` for seeding. T13 then consumes — no per-test cookie wrangling. Without this, every T13 test file reimplements ~20 LOC of session setup. Also: explicitly forbid `fetch` calls without going through the helper (lint or PR review).

### 13. T03 (Migration test): Idempotency claim under-tested
**Issue**: T03 says "Re-run migration on already-indexed DB → no-op, no error" — this only proves the migration doesn't crash. It doesn't prove the pre-flight SELECT also runs idempotently when the index already exists (does the pre-flight short-circuit, or does it always scan?). For a DB with 5M orgs, the pre-flight scan on every boot is a perf regression.
**Recommendation**: Either (a) modify pre-flight to skip when `idx_orgs_name` already exists in `sqlite_master`, with a test asserting the SELECT is not prepared/executed on subsequent boots (spy on `db.prepare`); or (b) document in acceptance that pre-flight always runs and add a perf benchmark: "10K orgs → pre-flight completes in <50ms." Currently neither.

### 14. T07 (Route dispatch): URI decode error path not unit-tested in dispatcher
**Issue**: T07 acceptance says "Routing matrix tests pass" but the test list includes "PATCH `/api/admin/orgs/o%2` → 400 BAD_PATH (malformed encoding)." This 400 is emitted from a try/catch around `decodeURIComponent` in the dispatcher. If implementer puts the try/catch around the wrong call (e.g., inside the handler instead), test passes but the 400 comes from handler not dispatcher. Test cannot distinguish.
**Recommendation**: Either (a) move `decodeURIComponent` into the handlers (T04 `validatePathParam` already exists for this — let handlers call it, eliminate dispatcher try/catch — simpler), or (b) assert the 400 response body has a marker like `{ code: 'BAD_PATH', source: 'dispatcher' }` (overkill). Recommend (a): delete the dispatcher try/catch, let `validatePathParam` in handlers do the work. Removes a duplicate error path and unifies the test target.
