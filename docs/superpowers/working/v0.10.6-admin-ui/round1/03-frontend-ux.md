# Round 1 review — Frontend / UX

**Reviewer lens**: vanilla HTML+CSS+JS dashboard conventions, CSP, a11y, error/loading states, mobile, i18n, ergonomics of role-change and destructive flows
**Spec under review**: `docs/superpowers/specs/2026-05-18-admin-ui-design.md`
**Reference**: `dashboard/public/index.html` (1201 lines, French `lang="fr"`, dark theme, single-file inline CSS+JS), `src/serve-http.ts:449-487` (static handler), `src/auth/html.ts:46-50` (CSP for the *auth* HTML pages only)
**Overall verdict**: NEEDS-WORK

The architectural shape (single file, vanilla, mirror `index.html`) is the right call for v0.10.6 scope. The frontend section of the spec is, however, written from ~10000 ft: it sketches a layout and a fetch flow but omits every concrete UX decision an implementer is forced to make — what does a 403 actually render? what does the role dropdown look like before save commits? what about the screen reader user? what about a 1280×800 laptop in a 350px-wide split window? And one specific factual claim is wrong: the dashboard does **not** ship with a CSP today, so the "follow the existing pattern" hand-wave gives implementers no policy to copy. Below are 11 concerns ordered by impact.

## Concerns

### 1. CSP claim is factually wrong; spec gives no CSP policy for the new page — MAJOR
**Description**: Spec §CSP says "The dashboard already serves with a CSP. Confirm the existing policy allows inline JS for the existing index.html." It does not. `src/serve-http.ts:479-483` (the `/dashboard/*` static handler) writes only `Content-Type` and `Access-Control-Allow-Origin: *` — no `Content-Security-Policy`, no `X-Frame-Options`, no `Referrer-Policy`. The CSP that `src/auth/html.ts:48` ships (`default-src 'none'; script-src 'none'; ...`) is for the *auth* HTML page bundle, not for `/dashboard/*`. So "follow the existing pattern" yields **no CSP at all**, plus an admin page that loads inside an iframe on any origin (no `X-Frame-Options`, no `frame-ancestors`) — a clickjacking primitive against role-change buttons. Worse: `Access-Control-Allow-Origin: *` on the static handler means a malicious origin can fetch `/dashboard/admin.html`, scrape it for endpoint URLs and class names, and design a targeted clickjack/replay payload. The spec also explicitly accepts "Inline-JS in admin.html" as a risk *because CSP currently allows it*, which is a non-sequitur — CSP isn't there, so there's nothing to allow.
**Recommendation**: Decide and write down the CSP for `/dashboard/admin.html` *in this spec*: minimum `default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; connect-src 'self'; img-src 'self' data:; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`. That requires extracting the inline JS to `admin.js` from day one (no `'unsafe-inline'` in `script-src` — that's the whole point). Also add `X-Frame-Options: DENY` and drop `Access-Control-Allow-Origin: *` from the static handler for admin.html specifically (or scope it to GETs of JSON only). Update `src/serve-http.ts` to set these headers on `/dashboard/admin.html` (and ideally `/dashboard/*` generally — index.html benefits too). Without this, the spec is shipping a regression vs. the security baseline that v0.7.1 established for auth pages.

### 2. Inline-JS-with-`innerHTML`-and-template-strings is an XSS landmine for admin data — MAJOR
**Description**: `index.html` heavily uses `innerHTML = \`...${value}...\`` with a thin `escapeHtml()` helper around *some* interpolations (598-681) but not all (e.g. 347, 548 emit raw `text` into the timeline; 855 emits agent fields raw). Admin data is the *worst* class of input to apply this pattern to: org names, user emails, and user display names come from third-party IdPs (Google/GitHub) and can legitimately contain `'`, `"`, `<`, even RTL override / zero-width characters used for unicode-spoofing attacks. The spec's threat model claims "client-side escape on render" (line 319) but provides no helper, no test, no lint, and no requirement that *every* interpolation use it. Given the existing precedent of half-escaped templates, implementers will almost certainly repeat the pattern. A user whose IdP name is `<img src=x onerror="fetch('/api/admin/users/'+adminId,{method:'PATCH',body:'{\"role\":\"admin\"}'})">` then becomes a stored-XSS-to-self-promotion attack against any admin viewing the user list.
**Recommendation**: Mandate a different DOM construction model for admin.html: build elements with `document.createElement` + `.textContent` for all user/org-supplied values; reserve `innerHTML` for static layout templates only. Provide a single `renderTable(rows, columns)` helper that takes column accessors and uses `textContent` internally. Add a unit test that scans `admin.html`/`admin.js` for `innerHTML\s*=` and fails CI unless the assigned value is a string literal. With a strict `script-src 'self'` CSP (concern #1) the impact of a stored XSS is bounded, but bounded ≠ safe — `fetch('/api/admin/...')` from the same origin still works, and that's the whole attack surface.

### 3. No CSRF cookie read strategy — `__Host-csrf` is not accessible to `document.cookie` if `HttpOnly` — MAJOR
**Description**: Spec line 55 and 251 say the client reads the CSRF token via `document.cookie` parsing. This only works if the CSRF cookie is set *without* `HttpOnly`. The spec doesn't state whether `__Host-csrf` is HttpOnly today, doesn't reference what `src/auth/csrf.ts` does, and doesn't define the contract. If the cookie is HttpOnly (which it should be for the session cookie — but possibly not for double-submit), the client breaks. If it's *not* HttpOnly, the spec should say so explicitly so the reviewer can evaluate whether non-HttpOnly is acceptable here. Additionally, `document.cookie` parsing is famously fiddly (URL-encoded values, attributes mixed in on some browsers, `;` inside values). Implementers will write a one-liner regex and ship a bug.
**Recommendation**: Either (a) verify `__Host-csrf` is non-HttpOnly today and document that fact in the spec, OR (b) expose CSRF token via a small `GET /api/auth/csrf-token` endpoint that returns `{ token: "<value>" }` (works regardless of cookie flags, and the response itself can be `SameSite`-cookie-gated). Provide the canonical `readCsrfToken()` helper in `admin.js` and reuse it from `index.html` too. Add a test for the cookie-parsing branch with edge cases (URL encoding, multiple cookies, missing cookie → throw a clear error rather than silently sending empty header).

### 4. Last-admin error path: 409 message is good but the UX flow around it is wrong — MAJOR
**Description**: Spec returns `{ error: "cannot demote last admin", error_description: "promote another user to admin first" }` and says "409 last-admin error → inline error message, no page reload". Good copy. But the UI flow described (role column has `[member ▾]` dropdown; "change triggers PATCH and inline confirmation toast") has the user *already changed the dropdown value before clicking save* (or worse: the change *is* the save, per a literal reading). When the 409 comes back, the dropdown is now visually showing `member` for a user who is still `admin` in the DB. The user sees a toast that says "promote another user first" but the dropdown they're staring at still says `member`. They will refresh, confused. Or they will click again, getting another 409. Or — and this is the real footgun — if they happen to *also* have a second admin (themselves), the operation succeeds and they have now silently demoted the wrong user. The dropdown semantic of "value changes immediately on selection" is incompatible with a confirmation-required write.
**Recommendation**: Spell out the role-change ergonomics explicitly in the spec. Recommended: dropdown is a *staging* control — selecting a value enables a "Save" button next to it; the row only commits on Save click. On 409, the dropdown auto-reverts to the previous value AND the inline error appears *anchored to that row*, not as a global toast. Toasts are wrong here: the operator needs to see "your demotion of *this specific user* was refused" with the row highlighted. Toasts vanish; the row context vanishes; the operator scrolls away confused. Additionally: surface a top-of-page banner whenever the admin count would drop to 1 (computed client-side from the user list) — pre-empt the 409 with "you are the only admin; promote another user before demoting yourself." This is the same information, surfaced before the operator wastes a click.

### 5. No loading, empty, or error states defined — MAJOR
**Description**: Spec describes "On page load: fetch /api/admin/orgs and /api/admin/users (parallel), populate tables." It does not describe: (a) what shows during the fetch (blank page? "Loading…"? skeleton rows? — implementers will pick "blank", which looks broken for slow networks), (b) what shows for an empty result (no orgs yet → empty `<table>` is invisible; user must guess whether the fetch failed or there really are zero orgs), (c) what shows when the backend is *down* (fetch rejects with TypeError; spec only handles `4xx/5xx` responses with `error_description`, not the network-error case), (d) what happens when one of the two parallel fetches succeeds and one fails (partially-populated UI with no indication that the other half is stale), (e) what shows when the user lands on /admin.html *not logged in* (spec says "401/403 → redirect to /login" but doesn't say what the user sees during the redirect; a flash of an empty admin page is a CSP/clickjack concern as well as a confusing UX).
**Recommendation**: For each table, define three render states explicitly: `loading` (skeleton rows with shimmer or "Loading orgs…" placeholder), `empty` (CTA: "No orgs yet. [Create your first org]"), `error` (inline error block with retry button + the last-known data preserved below). For network errors specifically, distinguish "fetch failed entirely" (offline / DNS / TLS) from "fetch returned 5xx" — the user actions differ (check VPN vs. contact ops). Add to the spec: "Before redirecting on 401/403, render a one-line 'Redirecting to login…' placeholder rather than an empty body, so users don't see a flash of unauthorized state."

### 6. No accessibility requirements: labels, focus management, keyboard nav, ARIA — MAJOR
**Description**: Spec is silent on accessibility. The implications are concrete: (a) "Click row → expands inline edit form" with no keyboard-equivalent activation — non-mouse users (keyboard, switch, screen reader) cannot edit orgs at all, (b) "+ New org button → modal form" with no focus-trap or restore — opening the modal leaves keyboard focus behind the modal, and on Escape there's no defined behavior, (c) role dropdown has no `<label>` association, (d) toasts have no `role="status"` or `aria-live="polite"` so screen reader users get zero feedback on success/failure, (e) the tab nav `[ Orgs ][ Users ]` is described in ASCII art but there's no statement of `role="tablist"` / `aria-selected` semantics, (f) tables have no caption or row/column header semantics. Admin tooling is precisely the surface where accessibility tends to be skipped "because the audience is small" — but the audience is also small enough that *one* a11y-dependent operator is 100% of your audience.
**Recommendation**: Add an Accessibility section to the spec with concrete requirements: (1) every `<input>` and `<select>` has a `<label>` or `aria-label`, (2) modal opens → focus moves to first input; Escape closes and restores focus to the trigger; focus is trapped inside while open (or use the native `<dialog>` element with `showModal()` which handles this for free in evergreen browsers — spec should pick one), (3) toasts are `<div role="status" aria-live="polite">` (success) and `aria-live="assertive"` (errors), (4) row-click-to-edit also responds to Enter/Space on a focused row OR (better) the row contains a real `<button>Edit</button>` rather than relying on row click, (5) tab nav uses `role="tablist"` + `aria-selected` + arrow-key navigation, (6) tables include `<caption>` and `<th scope="col">`, (7) all interactive elements have visible focus styles (default browser outline is fine; just don't `outline: none` without a replacement). Add an axe-core check to the Playwright e2e test.

### 7. No viewport meta or responsive plan; admin.html will be unusable on tablet/laptop split-screen — MAJOR
**Description**: `index.html` has no `<meta name="viewport">` (line 2-5 only sets charset and title). On mobile, that means the page renders at desktop width and is pinch-zoomed — barely usable for the read-only dashboard, but actively dangerous for a *mutation* UI where the role dropdown sits 4px from the "Delete" or "Save" hit target. The spec describes a fixed-pixel layout (250+1fr+6+300 column grid in the reference page) and says nothing about admin.html's responsive behavior. Real operator scenarios: admin gets paged at 2am, opens /admin.html on their phone to flip a role — tap lands on the wrong row. Or: admin runs the dashboard in a 400px-wide tile next to terminal+logs — the inline edit form overflows horizontally and the Save button is offscreen.
**Recommendation**: Spec must require `<meta name="viewport" content="width=device-width, initial-scale=1">` and a minimum responsive plan: (a) at <768px, tables collapse to card lists (one user per card, role dropdown + save button stacked), (b) modals are full-width on mobile, (c) tap targets ≥44×44px (the existing dashboard uses 24px buttons; admin must not). Define a tested breakpoint set. If responsive is out of scope for v0.10.6, then *gate the page behind a min-width check* — show "admin.html requires ≥1024px width" rather than ship a broken touch UI that silently mis-fires destructive operations.

### 8. Color contrast not specified; existing palette has known WCAG misses — MODERATE
**Description**: Existing `index.html` uses `#64748b` (slate-500) on `#0f0f1a` for panel titles and labels — that's a contrast ratio of ~3.7:1, below WCAG AA's 4.5:1 for normal text. It also uses `#94a3b8` (~5.5:1) which is borderline AA depending on font weight. Admin.html will inherit this palette per spec. For admin tooling, where "is this the org named `acme` or `acrne`?" is a real misread risk that translates to picking the wrong org to mutate, contrast matters more than on a read-only dashboard. The dark-on-darker pill colors (`#2a230a` for `.status-pill.open`) are even worse — text-on-background is in the 3-4:1 range. None of this is called out, so the implementer copies the variables and ships the same problems on a higher-stakes surface.
**Recommendation**: Spec should either (a) define a small darker-text/brighter-background admin-only palette that hits AA 4.5:1 on all text, or (b) audit the existing palette explicitly and call out which variables to swap for admin.html (`--muted: #94a3b8` → `--muted: #cbd5e1` etc.). The pills indicating role (admin/member) and operation status (saving/saved/error) deserve special attention — these convey state via *color alone* today, which fails WCAG 1.4.1; pair each color with an icon or text marker (✓ saved, ⏳ saving, ✕ failed).

### 9. Internationalization: existing UI is French-only, admin spec is implicitly English — MODERATE
**Description**: `index.html` is `lang="fr"` and ships French strings throughout ("En attente d'événements…", "Agents en ligne", "Connecté", "Quota indisponible"). The spec's example UI copy is English ("New org", "Logged in as", "promote another user to admin first"). Implementer must pick one. If they default to English to match the spec, admin.html is the only French-default deploy that suddenly has an English admin surface — jarring and inconsistent. If they translate, the spec's literal copy (especially the load-bearing 409 error_description which is *server-emitted*) needs French versions, and the server has to decide whether error messages are i18n'd server-side or client-side. The spec also doesn't address `lang` attribute, `dir` (RTL languages), date formatting for `last_login_at` (the spec returns ISO timestamps; will the UI render them via `toLocaleString()` or hard-code a format?), or number formatting for user counts.
**Recommendation**: Pick one of: (a) admin.html is French to match the deploy ("Nouveau org" / "Aucun org" / etc.) and the server's `error_description` is the *machine-readable* signal while the client picks the display copy, OR (b) admin.html is intentionally English-only with a brief justification ("operator tool, expected audience reads English"). State the choice. If (a), introduce a tiny client-side string table (`const i18n = { newOrg: "Nouveau org", ... }`) so the next translator has one file to edit. For timestamps, mandate `new Date(iso).toLocaleString()` (not raw ISO) — operators in different timezones currently see UTC and have to mentally convert.

### 10. `truncated: true` UX is undefined; 500-row cap will silently lie to operators — MODERATE
**Description**: Spec returns `{ users: [...], truncated: true }` for >500 users but doesn't say what the UI does with that boolean. Implementer-default: ignore it. Result: operator searches for "alice@bigcorp.com", doesn't find her in the rendered 500, concludes she doesn't exist or her account is missing, and either creates a duplicate-via-IdP-relogin or files a false bug. There's also no client-side filter on the list (the spec mentions only a server-side `?org=` filter) — so even with `truncated: false`, scanning 500 rows by eye to find one email is slow and error-prone. And the spec's threat model justifies the cap as "mass scrape mitigation," but a real attacker scrapes by iterating `?org=` values across all orgs, so the cap protects against nothing while degrading the legitimate-operator workflow.
**Recommendation**: (a) Render `truncated: true` as a prominent banner at the top of the user table: "Showing 500 of >500 users. Filter by org or use the search field to narrow results." (b) Add client-side filter input above the user table that filters the loaded 500 by email/name substring. (c) Reconsider the cap: either ship simple cursor pagination now (offset+limit, return `next_offset`) or raise the cap to something that fits realistic small/medium tenants (5000? — at 500 bytes/row that's 2.5MB, fine over the wire). (d) If you keep the 500 cap, log a server-side warning every time `truncated: true` fires, so operators know they're hitting it.

### 11. "Are you sure?" prompts missing for irreversible-feeling actions — MODERATE
**Description**: Spec has zero confirmation dialogs. Role demotion (admin → member) is functionally reversible (promote them back), but if the operator demotes the *wrong* admin, that admin is locked out of admin tooling and can't undo it themselves — they need another admin to act. The spec already protects against demoting the *only* admin (409 server-side) but does not protect against the much more common "demoted the wrong person of N admins" case. Similarly, `PATCH /api/admin/orgs/:id` with `allowlist_github_org: null` clears an allowlist — that change cascades: next login from someone in that org may be rejected. No confirm. The spec's "No undo button. Audit log is the recovery mechanism" line is correct in principle but doesn't apply at the *click-time*; once an admin is logged out by a typo demotion, "look at audit log" is the wrong tier of recovery for a 2-second action.
**Recommendation**: Require a confirmation step for: (a) role change (especially demotion) — show a "Demote `alice@acme.com` from admin to member?" modal with the user's full identity displayed, requiring an explicit click, (b) allowlist clear (setting to null) — confirm "Clear GitHub allowlist for org `Acme`? Users matching `acme-corp` will no longer be auto-admitted via GitHub OAuth." (c) name changes don't need confirm — low impact, easy to spot-fix. Use the native `<dialog>` element to avoid building a focus-trap from scratch. Confirmations are *the* lowest-cost UX guard against the wrong-row-clicked class of operator error, and the spec's audit-log recovery story does not substitute for them.

### 12. Inline-JS maintainability cliff: the 500-line ceiling is already breached on paper — MINOR
**Description**: Spec line 219 says "Keep the new file ≤500 lines total (HTML + inline CSS + inline JS). If it grows beyond that, split into admin.html, admin.css, admin.js siblings." Realistic line accounting for what the spec describes — header, tab nav, two tables with edit affordances, modal form, toast system, ~5 fetch flows with error handling, CSRF helper, escape helper, loading/empty/error state renderers (per concern #5), accessibility focus management (per concern #6), responsive breakpoints (per concern #7), confirmation dialogs (per concern #11), and a thin i18n table (per concern #9) — is 800-1200 lines minimum, mirroring index.html which is 1201 lines for a *read-only* surface. The 500-line budget is fictional; implementers will either (a) inline everything anyway and produce an unmaintainable monolith, or (b) thrash mid-implementation deciding when to split. Worse, concern #1 already requires extracting JS to `admin.js` for CSP reasons, so the "single file" goal is moot from the start.
**Recommendation**: Drop the 500-line goal. Start with three files from day one: `admin.html` (markup + `<link rel="stylesheet">` + `<script src="admin.js" defer>`), `admin.css`, `admin.js`. This is required for a tight CSP anyway (#1), enables `defer` for non-blocking JS, and gives future contributors a sane diff surface. Update the static handler test for the two new files (`.css` and `.js` MIME types are already in the handler at line 472-477, no change needed). Keep `admin.js` itself under ~600 lines by extracting `csrf.js`, `dom.js` (the createElement helpers from concern #2), and `i18n.js` (concern #9) as separate modules loaded via `<script>` tags — modern browsers parse all of them in parallel and `defer` preserves order.

## Top-3 must-fix before V2

1. **CSP + frame protection** (#1) — design intent of v0.10.6 says "no new auth model" but the spec silently ships a regression vs. v0.7.1's auth-page CSP baseline. Define the policy, extract the JS, set the headers.
2. **Last-admin/role-change ergonomics** (#4 + #11) — this is the single highest-stakes click in the entire UI, and the spec describes it in two lines. Specify the staging-then-save flow, the 409-handling rollback, the pre-emptive last-admin banner, and the confirmation modal. Without this, the spec's correct server-side 409 protection is undermined by a UI that makes the operator mis-perceive what changed.
3. **A11y + responsive minimum bar** (#6 + #7) — admin tooling typically gets a pass on these "because the audience is small," and that's exactly why they fail closed for the one operator who needs them. The cost to add labels, viewport meta, and a `<dialog>` for modals is hours, not days, and unblocks future contributors from inheriting an inaccessible foundation.
