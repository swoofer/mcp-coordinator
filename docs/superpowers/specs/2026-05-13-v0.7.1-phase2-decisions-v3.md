## B-NEW-1 — `token_epoch` read source (resolved)

**Issue** (4 agents): NR10 says "trust-signature on Bearer/cookie, no DB hit per request" but Q8 mandates `claims.iat >= user.token_epoch` on every JWT verify. Internally contradictory.

**Resolution**: In-memory LRU cache.

```
token_epoch lookup strategy:
- Process-local LRU cache keyed by user_id, capacity 10K entries, TTL 60s
- Cache miss: SELECT token_epoch FROM users WHERE id = ?
- On logout-all or admin-revoke: invalidate cache entry locally
- Multi-instance Phase 2: cache lag = TTL (60s); document as known trade-off
- Phase 5 multi-instance: replace with Redis pub/sub invalidation channel
```

Spec must state explicitly: **"Phase 2 is single-instance deployment; cache invalidation across instances is Phase 5 work."**

`token_epoch` comparison: strict `claims.iat >= user.token_epoch`. **Zero clock-skew leeway** on epoch (overrides Q3 ±30s rule). Incident response must be immediate-effect.

NTP rollback safety: when bumping `token_epoch`, server uses `MAX(now, current_token_epoch + 1)` to ensure monotonicity even under negative NTP step.

## B-NEW-2 — 10s grace window token theft bypass (resolved)

**Issue** (3 agents — pentester C1, OWASP, crypto): Algorithm returns cached successor to whoever presents parent jti within 10s. Attacker who steals refresh can race the legit user, receive new pair WITHOUT triggering family revoke.

**Resolution**: Bind successor to original requester via request fingerprint.

```sql
ALTER TABLE refresh_tokens ADD COLUMN replay_count INTEGER NOT NULL DEFAULT 0;
ALTER TABLE refresh_tokens ADD COLUMN consumer_fingerprint TEXT;
-- consumer_fingerprint = SHA-256(client_ip + "|" + user_agent) computed at rotation time
```

Revised algorithm:
```
on /api/auth/refresh(token, req):
  claims = jwtVerify(token)
  row = SELECT * FROM refresh_tokens WHERE jti = claims.jti
  fingerprint = sha256(req.ip + "|" + req.userAgent)
  
  if row.revoked_at IS NOT NULL:
    if row.revoked_reason == 'rotated' AND (now - row.revoked_at) < 10s:
      # Concurrent retry — check fingerprint
      successor = SELECT * FROM refresh_tokens WHERE parent_jti = row.jti
      if successor.consumer_fingerprint == fingerprint:
        # Legit retry from same client — return cached successor (re-mint JWT bytes deterministically)
        return mint(successor.jti, successor.family_id, ...)
      else:
        # Different client = token theft attempt within grace window
        UPDATE refresh_tokens SET replay_count = replay_count + 1 WHERE jti = row.jti
        if row.replay_count + 1 >= 3:
          # Threshold reached → revoke family
          UPDATE refresh_tokens SET revoked_at=now, revoked_reason='reuse_detected' WHERE family_id=row.family_id AND revoked_at IS NULL
          audit('auth.refresh.chain_revoked', ...)
          return 401
        else:
          audit('auth.refresh.suspicious_replay', { replay_count })
          return 401  # don't reveal the successor
    elif (now - row.revoked_at) >= 10s OR row.revoked_reason != 'rotated':
      # Hard reuse - revoke immediately
      UPDATE refresh_tokens SET revoked_at=now, revoked_reason='reuse_detected' WHERE family_id=row.family_id AND revoked_at IS NULL
      audit('auth.refresh.chain_revoked', ...)
      return 401
  
  # Normal rotation
  newJti = randomUUID(); newFingerprint = fingerprint
  BEGIN TRANSACTION
    UPDATE refresh_tokens SET revoked_at=now, revoked_reason='rotated' WHERE jti=claims.jti
    INSERT INTO refresh_tokens(jti=newJti, family_id=row.family_id, parent_jti=row.jti, consumer_fingerprint=newFingerprint, ...)
  COMMIT
  return new pair
```

The 3-attempt `replay_count` threshold (per abuse agent) prevents single-replay false positives from SSE/mobile reconnect storms while still catching theft (attacker won't have matching fingerprint).

**Note for spec**: re-minting "the same JWT bytes" is impossible without storing the signed JWT. Solution = re-mint a fresh JWT with the SAME `jti`, `family_id`, `iat`, `exp` claims (deterministic given stored row + clock). Spec must pin the mint function as pure-of-claims.

## B-NEW-3 — Service account hygiene (resolved)

**Issue** (5 agents): NR1 long-lived JWT, no TTL cap, no rotation, no attribution, no inventory.

**Resolution**: Service account discipline as Phase 2 hard requirement.

```ts
// NR1 revised
mcp-coordinator issue-service-token \
  --user=<id> --org=<id> --scope=<read|write|admin> \
  --ttl=<duration> --reason="<text>"
```

Constraints:
- `--ttl` REQUIRED, max **90 days** (hardcoded ceiling; not env-configurable)
- `--reason` REQUIRED (free text, ≥10 chars, logged)
- Issuing CLI requires admin OAuth (no anonymous mint) — verifies actor token via authenticateRequest before minting
- JWT claim `service_account: true`, `issued_by: <admin_user_id>`, `scope: 'read'|'write'|'admin'`, `family_id: 'service:<uuid>'` (literal format, regex `^service:[0-9a-f-]{36}$`)
- Audit events: `auth.service_token.issued` (with actor_user_id, target user_id, scope, ttl, reason), `auth.service_token.used` (sampled, max 1 per hour per token to avoid spam), `auth.service_token.revoked`

**`token_epoch` applies to service accounts** (override NR10 trust-signature for `service_account=true` claim — these JWTs ARE validated against DB per request). Acceptable perf hit: service tokens are low-volume CI traffic.

CLI verb `mcp-coordinator list-service-tokens` (Phase 2 mandatory) shows: jti, issued_by, target_user, scope, ttl, last_used_at, status.

`refresh_tokens.last_used_at` updated on every service-token request (not refresh — service tokens don't rotate).

Rotation skip predicate (refresh handler): `if claims.service_account === true: return 400 INVALID_GRANT { message: "Service tokens do not rotate; mint a new one via admin CLI" }`.

## B-NEW-4 — Apply Q1 pattern to Q2 (resolved)

**Issue** (3 agents): `COORDINATOR_GITHUB_ORG` as global env var creates dual-mode (self-host vs Phase 5 SaaS). Same lesson learned from Q1 not applied.

**Resolution**: Add `orgs.allowlist_github_org` column; env var seeds the bootstrap org.

```sql
ALTER TABLE orgs ADD COLUMN allowlist_github_org TEXT;  -- nullable
CREATE INDEX idx_orgs_allowlist ON orgs(allowlist_github_org);
```

Boot flow:
- If `COORDINATOR_GITHUB_ORG` env set AND no row exists with `allowlist_github_org = $env`: INSERT bootstrap org row with `id = <uuid>`, `name = $env`, `allowlist_github_org = $env`. Persist.
- Subsequent boots: env var change is detected and logged, but bootstrap org row is NOT modified (admin must use admin CLI to change allowlist).
- Allowlist check at callback: `SELECT id FROM orgs WHERE allowlist_github_org = $github_org_login` (Phase 2: exactly one row matches; Phase 5: multiple rows = SaaS multi-tenant).

`getOrgSetting(org_id, key, envDefault)` shim: now reads from `orgs.<config_column>` first, env fallback. TTLs, idle timeout, allowlist all flow through this. **Spec must enforce**: all Phase 2 config reads go through the shim, not direct `process.env.X`.

Phase 5 transition: drop app-layer "exactly one row" invariant; allow multiple `orgs` rows. Zero schema change.

## B-NEW-5 — `listMemberships` cache + stale-on-error (resolved)

**Issue** (4 agents): No-cache on every refresh = GitHub rate limit hit + GitHub outage = mass logout storm.

**Resolution**: 60s positive cache + stale-on-error window.

```
listMemberships cache:
- Key: SHA-256(user_id + "|" + idp_provider)
- Storage: process-local LRU, capacity 10K, TTL 60s positive
- Stale-on-error: if GitHub returns 5xx/timeout AND cached entry exists AND now - cached.ts < 10min: serve cached, emit metric `idp_stale_served_total`
- Beyond 10min stale window OR no cached entry: return IdPTransientError → 503
```

Trade-off documented in spec: **removed-member access lag = max(60s, refresh_interval) ≤ 16 minutes in normal operation; up to 10 minutes additional during GitHub outage.**

Metrics: `idp_api_calls_total{endpoint,outcome}`, `idp_cache_hits_total`, `idp_cache_misses_total`, `idp_stale_served_total`, `idp_rate_limit_remaining` (gauge).

## B-NEW-6 — Audit durability tiers (resolved → NR13)

**Issue** (3 agents): NR10 async queue can drop events on SIGKILL/OOM. Critical events for SOC 2 must not drop.

**Resolution**: Two-tier audit write strategy.

### NR13 — Audit durability tiers

**Tier 1 (synchronous, never drop)** — written before HTTP response returns, single INSERT, no queue:
- `auth.refresh.chain_revoked`
- `auth.refresh.reuse_detected`
- `auth.refresh.suspicious_replay`
- `auth.state.replay`
- `auth.login.denied.not_in_org`
- `auth.login.locked` (lockout fires)
- `auth.token.revoked`
- `auth.logout.global`
- `auth.service_token.issued`
- `auth.service_token.revoked`
- `auth.admin.bootstrapped`
- `recovery.*` events

**Tier 2 (async queue, may drop under pressure)** — batched 50 rows / 100ms:
- `auth.login.success`
- `auth.login.failure`
- `auth.refresh.rotated`
- `auth.refresh.idle_expired`
- `auth.device.*`
- `auth.user.created`
- `auth.user.provisioned`
- `auth.logout.local`
- `auth.invalid_token`
- `auth.service_token.used`
- `config.boot`

Queue policy:
- Bounded size 10K rows
- Backpressure: block producer (refresh hot path) for ≤100ms then drop with `audit_drops_total++`
- SIGTERM: drain queue with 5s timeout; remaining drops logged + audit row `system.shutdown.audit_loss`
- Alert: `audit_drops_total > 0` → CRITICAL page

## B-NEW-7 — SQLite vs Postgres for audit immutability (resolved)

**Issue** (2 agents — SOC 2, HIPAA): NR4 "DB-level revoke UPDATE/DELETE on audit_log to app role" doesn't apply to SQLite (no role system).

**Resolution**: Two-tier deployment policy.

```
SQLite deployment (Phase 2 default):
- App-layer enforcement only (writes through audit() helper, never raw SQL UPDATE/DELETE on audit_log in production code)
- WAL mode + filesystem permissions hardening (db file 0600, parent dir 0700)
- Append-only by code convention; spec mandates a CI lint check that grep -r "UPDATE audit_log\|DELETE FROM audit_log" returns zero matches outside migration files
- NOT regulated-grade integrity (SOC 2 Type II + HIPAA require stronger)

Postgres deployment (Phase 4+ for regulated workloads):
- REVOKE UPDATE, DELETE ON audit_log FROM coordinator_app;
- Separate role coordinator_audit_writer with INSERT-only grant
- Documented as prerequisite in regulated-deployment guide
```

V3 explicitly states: **"HIPAA / SOC 2 Type II deployment requires Postgres backend and is deferred to Phase 4."** This sets honest expectations for regulated buyers and unblocks Phase 2 ship.

## B-NEW-8 — Rate limiting normative table (resolved → NR11)

**Issue** (abuse agent + 2 others): Spec mentions 429 in NR5 but no per-endpoint policy. Without rate limiting, NR10 metrics observe attacks they can't stop.

### NR11 — Rate limiting (normative)

| Endpoint | Per-IP limit | Per-account/key | Notes |
|---|---|---|---|
| `GET /auth/login` | 30/min | — | OAuth init |
| `POST /api/auth/oauth/token` (code grant) | 10/min | — | + 100/s global circuit break |
| `POST /api/auth/oauth/device_authorization` | 5/min | 20/hr per IP | DoS shield + phishing throttle |
| `POST /api/auth/oauth/token` (device poll) | 60/min per IP | hard cap 1/5s per `device_code` | RFC 8628 slow_down enforced |
| `POST /auth/device/approve` | 10/min | 20/hr per `user_id` | Phishing throttle |
| `POST /api/auth/oauth/token` (refresh grant) | 60/min | 30/min per `family_id` | Retry-storm cap |
| `POST /api/auth/logout` | 30/min | — | Idempotent |
| `POST /api/auth/logout-all` | — | 5/hr per `user_id` | Epoch-bump abuse prevention |
| `GET /api/auth/me` | 600/min | — | UX path, generous |
| `POST /api/auth/revoke` (RFC 7009) | 30/min | — | Same as logout |
| Audit ingest (queue) | 1000/s global | 50/s per IP | Drop with metric |

Implementation: in-memory token bucket per (endpoint, identifier). 429 response with `Retry-After: <seconds>` header. Metric `rate_limit_blocked_total{endpoint, identifier_type}`.

**Login lockout** (compliance B-NEW-2): 5 failed `auth.login.failure` per identifier (hashed_github_login OR IP, whichever matches first) within 15min → 15min lockout. Emit `auth.login.locked`. Configurable via `COORDINATOR_LOGIN_LOCKOUT_THRESHOLD` (default 5), `_WINDOW` (default `"15m"`), `_DURATION` (default `"15m"`). Bootstrap admin exempt (one-shot anyway).

## B-NEW-9 — Device flow consent phishing defense (resolved)

**Issue** (abuse agent): `verification_uri_complete` + no rate limit on init + no per-user pending cap = phishing scale attack.

**Resolution**: Defense layers.

1. Rate limit on `/oauth/device_authorization` (NR11 above)
2. **Per-user pending device approvals cap**: ≤3 unapproved `device_auth_requests` per `approved_user_id` at any time. Older ones get auto-denied.
3. **Device approve page shows requester context**: GitHub login, IP, User-Agent (parsed for human-readable browser/OS), approximate geo from IP (best-effort, no PII stored), timestamp of request. User checkbox "I recognize this device" + Approve button.
4. **Distinct CSRF token per `user_code`** (not per session) — prevents replay of an old CSRF token across different device codes.
5. Audit `auth.device.approved` row includes both `actor_user_id` (the approver) AND requester IP/UA snapshot for forensics.

Updated `device_auth_requests` schema:
```sql
ALTER TABLE device_auth_requests ADD COLUMN requester_ip TEXT;
ALTER TABLE device_auth_requests ADD COLUMN requester_user_agent TEXT;
ALTER TABLE device_auth_requests ADD COLUMN requester_country TEXT;  -- best-effort, may be NULL
ALTER TABLE device_auth_requests ADD COLUMN org_id TEXT REFERENCES orgs(id);  -- B-NEW-cost: tenant attribution
```

## B-NEW-10 — Backup-induced security regression (resolved → NR12)

**Issue** (disaster recovery agent — CRITICAL): SQLite restore from t-1d → `token_epoch` and `revoked_at` rollback → tokens explicitly revoked during incident response become valid again. Silent security regression.

### NR12 — Restore detection + reconciliation

Schema:
```sql
CREATE TABLE IF NOT EXISTS system_state (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

Boot-time check:
1. Compute `max_observed_iat = MAX(SELECT created_at FROM audit_log)`, `max_refresh_iat = MAX(SELECT created_at FROM refresh_tokens)`, `max_state = MAX(updated_at FROM system_state)`
2. Compare to wall clock. If `now - max(max_*) > 5 minutes` AND `COORDINATOR_ALLOW_RESTORE != true`: refuse to start with error `boot.restore_suspected` + log instructions.
3. If `COORDINATOR_ALLOW_RESTORE=true` is set: proceed with **restore reconciliation**:
   - `UPDATE users SET token_epoch = strftime('%s','now')` (bump ALL users)
   - Insert `system_state` row `{key='last_restore_at', value=now}`
   - Emit audit `recovery.token_epoch_global_bump` and `recovery.completed`
   - Log loud warning to ops: "Service restored from backup; all sessions invalidated. Users must re-authenticate."
4. After successful boot post-restore: ops MUST unset `COORDINATOR_ALLOW_RESTORE` env var.

Operational doc `docs/ops/backup-restore.md` (NR7 #11):
- Recommended: **litestream WAL shipping** to S3-compatible store, 1-min RPO target
- Recommended: daily `sqlite3 .backup` snapshot, 30d retention
- Quarterly restore drill required for SOC 2 readiness
- Restore procedure: stop coordinator → restore DB → `export COORDINATOR_ALLOW_RESTORE=true` → boot → verify `recovery.completed` audit row → unset env → publish all-users-re-auth notice

## B-NEW-11 — Account auto-provisioning gate (resolved)

**Issue** (abuse agent): Every successful OAuth callback INSERTs `users` row. Attacker with N GitHub accounts in COORDINATOR_GITHUB_ORG creates N rows (disk fill, audit log spam).

**Resolution**: Configurable auto-provisioning.

```
COORDINATOR_AUTO_PROVISION env var:
- "true" (default Phase 2): first OAuth callback creates user row automatically
- "false" (recommended for regulated): user must be pre-created by admin (auth.login.failure with code USER_NOT_PROVISIONED if no row exists)
- "approval_required" (Phase 3): callback creates row with role='pending', admin approves via CLI before role becomes 'member'
```

Phase 2 ships `true` and `false` modes. `approval_required` deferred to Phase 3.

When `false`: admin pre-creates via CLI `mcp-coordinator add-user --github-login=<login> --org=<id> --role=<member|admin>`.

## Contrarian alternatives — final decisions

After review of Round 2 contrarian + 2-year regret recommendations:

1. **`token_epoch`** — **KEEP**. It's the break-glass primitive for incident response. Regret 2028 saying "used 0 times in prod" is hindsight — insurance has value precisely when never used. Cost (1 col + LRU cache) is trivial vs the SOC 2 / HIPAA immediate-revocation requirement.

2. **`user_agent_hash` on oauth_state** — **CUT**. Brittle (Chrome auto-update mid-flow, mobile→desktop hand-off — which is the PRIMARY device flow use case). Legitimate-flow breakage rate non-trivial. Mix-up defense already provided by `provider` column + PKCE + `consumed_at` one-time use. RFC 9700 §4.7 is "should," not "must." Schema column and callback verification both removed.

3. **HMAC-bound CSRF** — **KEEP**. Defense-in-depth against same-site XSS-chained CSRF. Cost: HKDF-derived key (zero env var). Crypto reviewer Round 2 validated the pattern.

4. **`.well-known/oauth-authorization-server`** — **KEEP**. ~30 lines, RFC 8414 standard, unblocks SDK consumers Phase 4 immediately. Cutting = tech debt for no gain.

5. **18 audit events** — **KEEP all 18**. Round 2 SOC 2 reviewer confirmed "evidence-grade." Trimming saves spec text, loses forensics value.

6. **Encryption-at-rest forward to Phase 2** — **STAY DEFERRED to v0.7.5**. Forward = scope creep (SQLCipher dep, migration, key management). v0.7.5 is the right venue. Phase 2 spec MUST explicitly document the gap + mitigations:
   - Filesystem permissions: DB file 0600, parent dir 0700, enforced at boot
   - JWT and session cookie payload minimization (no PII; only `sub`, `jti`, `iat`, `exp`, `iss`, `family_id`, `active_org_id`)
   - NR4 audit redaction allowlist (no raw tokens persisted)
   - Threat-model.md (NR7 #6) explicitly names backup leak as Phase 2 known weakness
   - v0.7.5 release blocks production deployment for any party with EU operators or regulated workloads (documented in threat model)

### Schema impact of decision #2 (CUT user_agent_hash)

Remove from `oauth_state` schema:
- `user_agent_hash TEXT` column
- index/check involving user_agent_hash (none, was simple TEXT)
- Callback handler logic: recomputing SHA-256(req.headers['user-agent']) and comparing — removed
- B-NEW-12 ambiguity #6 (NULL UA policy) — moot, removed

State binding is still defended by:
- `provider` column on `oauth_state` (mix-up defense per RFC 9700 §4.4)
- 256-bit CSPRNG `state` value (replay defense)
- `consumed_at` atomic CAS (one-time use)
- PKCE S256 code_verifier (RFC 7636 binding to client device)
- 10min absolute TTL on state row

This is sufficient for Phase 2 threat model. If Phase 4 federation introduces multiple IdPs, revisit with signed-cookie state binding (RFC 9700 §4.7 stronger pattern).
