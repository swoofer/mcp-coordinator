# v0.8 Enterprise Compliance — Design Sketch (NOT a full spec)

**Status**: lightweight design sketch — capture-pour-ne-pas-oublier, NOT an approved implementation plan
**Owner**: swoofer
**Convert to spec when**: a real enterprise client demands one or more of the listed items, OR an audit (SOC 2 / GDPR / HIPAA / similar) is scheduled within 6 months
**Shipped state at write time**: v0.7.0 shipped (auth foundation). v0.7.5 (SQLCipher whole-DB encryption) is **spec'd but not yet shipped** — see `2026-05-11-encryption-at-rest-design.md`.

## Purpose

mcp-coordinator's v0.7 (auth, shipped) and v0.7.5 (encryption at rest, spec'd) explicitly defer a set of enterprise-compliance features to a future v0.8. This sketch captures the architectural intent so the deferral is documented and the hooks already baked in earlier versions are visible.

**This is not a spec.** It commits to nothing. When real client requirements arrive, brainstorm fresh against THOSE requirements and write the actual spec (which may diverge significantly from what's sketched here).

## What's already enabled (hooks shipped in v0.7; v0.7.5 spec'd)

These v0.8 features are NOT starting from scratch. v0.7 ships the structural foundation; v0.7.5 (spec'd) will extend it:

| v0.8 feature | Hook already in place |
|---|---|
| Column-level encryption | `EncryptionProvider` interface in `src/security/encryption.ts` accepts `context: {org_id, column}` (shipped in v0.7). v0.7 ships `PassthroughEncryption` (no-op stub); v0.7.5 (spec'd) will replace with SQLCipher whole-DB; v0.8 layers per-column on top. |
| Per-org DEK (BYOK) | `org_id` baked into JWT + every table from v0.7 Phase 1. Per-org key derivation slots into `EncryptionProvider`. |
| GDPR /export endpoint | `audit_log` table from v0.7 Phase 1 captures all data access. All sensitive tables have `org_id` for scoping. |
| GDPR /delete endpoint | Same. ON DELETE CASCADE behavior via FK on `org_id` makes "forget user X" tractable. |
| Retention policies | `audit_log.created_at`, `thread_messages.created_at`, etc. already indexed for time-window queries. |
| Audit log surface UI | `audit_log` table is the data layer; v0.8 adds a UI panel + `GET /api/audit?since=...&action=...` aggregation endpoint. |

In short: **the work in v0.8 is feature implementation on existing schema/interfaces, not architectural refactor.** Estimated effort once requirements are concrete: 3-4 weeks for typical enterprise tier.

## The 6 items (1 paragraph each)

### 1. Column-level encryption

Encrypt sensitive columns (`thread_messages.content`, `threads.plan`, `action_summaries.summary`, `audit_log.metadata`, possibly `reasoner_cache.verdict_json`) at the application layer using per-org DEKs, on top of v0.7.5's whole-DB encryption. The threat model jumps from "backup theft" (v0.7.5) to "insider with master key but no per-org DEK can't read other tenants' data". Implementation: `EncryptionProvider.encrypt(plaintext, {org_id, column})` returns base64 ciphertext; reads use `decrypt`. For LIKE / equality searches without leaking plaintext, an HMAC index is stored alongside (search by `HMAC(value, org_key)`). Significant write-path overhead (~20-40% on insert/update of encrypted columns).

### 2. Per-org DEK (tenant key isolation)

Each org has its own Data Encryption Key (DEK), derived from the master key + `org_id` via HKDF-SHA256. Stored encrypted-at-rest in the `orgs` table (wrapped with the master KEK). Compromise of one tenant's DEK does not leak any other tenant. Key derivation hierarchy: master KEK → per-org DEK → per-column nonces. Rotation per org without affecting other orgs. Required precondition for serious multi-tenant SaaS deployment.

### 3. BYOK (Bring Your Own Key)

Enterprise tier where the customer provides their own KMS endpoint instead of using mcp-coordinator's. AWS KMS / GCP KMS / Vault per-org config. The customer holds the master KEK; mcp-coordinator never sees the unwrapped key — it sends ciphertext to the KMS for unwrap on each boot, caches the unwrapped DEK in memory. Killing the KMS connection (deleting the customer's KMS key) makes the data unreadable globally. Required for: regulated industries (healthcare, finance) and large enterprise clients who insist on key sovereignty.

### 4. GDPR /export endpoint

`GET /api/orgs/<org_id>/export?user_id=<id>&format=json|csv` returns all personal data associated with a specific user across all tables. Required by GDPR Article 15 (Right of Access) and 20 (Right to Data Portability). Output: JSON archive with thread messages they wrote, file activity they triggered, action summaries authored, audit log entries naming them. Async generation (large export → async job + signed URL). Audit-logged. Authorization: admin-only OR the user themselves with refresh token.

### 5. GDPR /delete endpoint

`DELETE /api/orgs/<org_id>/users/<user_id>?confirm=...` cascades deletion across all tables that reference the user. Required by GDPR Article 17 (Right to Be Forgotten). Tricky cases: thread messages they wrote (delete? anonymize?), audit log entries naming them (anonymize but preserve for compliance audit), refresh tokens (revoke + delete). Default: anonymize-then-tombstone (replace user_id with `deleted_<hash>` placeholder rather than NULL/DELETE — preserves data integrity while honoring forget request). Audit-logged at the `auth.user.deleted` action.

### 6. Audit log surface UI

`GET /api/audit?since=<dur>&action=<glob>&user_id=<id>&org_id=<id>` aggregates from the `audit_log` table. Dashboard panel (alongside "Conflict signals" from v0.6) shows recent admin actions, failed login attempts, sensitive data access. Export to CSV. SOC 2 auditors typically demand: 1-year retention, immutability (append-only), tamper-evident chain (HMAC of previous row). v0.8 adds the export + UI; v0.8.1 could add the tamper-evident chain if a client demands it.

### Retention policies (auto-delete by age)

Bonus 7th: auto-delete by age policy per-table, per-org. Default `thread_messages` keeps 90 days, `audit_log` keeps 1 year, `file_activity` keeps 30 days. Configurable per org (`org.retention_config` JSON column). Background sweeper (reuses the v0.6 sweeper pattern) deletes rows beyond TTL. Required by GDPR data minimization principle.

## Trigger events for converting this sketch into a real spec

| Trigger | Likelihood | Response |
|---|---|---|
| Real client asks for column-level encryption or BYOK | Most likely trigger | Brainstorm fresh against THEIR specific requirements (industry, scale, KMS choice). Convert sketch → spec for #1, #2, #3 first. |
| SOC 2 audit scheduled in < 6 months | Medium | Convert sketch → spec for #6 + retention policies first. Then #4, #5 for GDPR overlap. |
| GDPR-heavy EU client | Medium | Convert sketch → spec for #4, #5 + retention first. Then column-level if data classification demands. |
| Pharma / financial / regulated industry client | Lower (initial market = tech teams) | Full v0.8 + likely v0.8.1 with HIPAA-specific additions (immutable audit log chain, BAA template, etc.) |
| Year passes with no client demand | Possible | Sketch stays as roadmap signal. v0.6 / v0.5 evolve. Don't write the spec speculatively. |
