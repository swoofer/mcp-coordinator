## What Phase 2 adds (rough scope)

### New endpoints
- `POST /api/auth/oauth/authorize` — initiate OAuth flow (state + PKCE generation)
- `GET /api/auth/oauth/callback` — provider redirect target; exchange code for user info, mint our JWT
- `POST /api/auth/oauth/device/code` — RFC 8628 Device Authorization Grant initiation
- `POST /api/auth/oauth/device/token` — Device Flow poll endpoint
- `POST /api/auth/oauth/device/approve` — browser-side approval (signed-in user clicks "allow")
- `POST /api/auth/logout` — revoke current refresh token + clear server-side state
- `GET /api/auth/me` — return current user + org context (UX helper)

### New IdP provider
- `GitHubProvider implements IdPProvider`
  - `buildAuthUrl(state, redirectUri, codeChallenge)` → GitHub `/login/oauth/authorize`
  - `exchangeCode(code, redirectUri, codeVerifier)` → POST to `/login/oauth/access_token` + GET `/user` + GET `/user/emails`
  - `idp_org_id` resolution from `/user/orgs` (optional Phase 2.5 — first cut: 1 user = 1 org defaulting to user-email-domain)

### Refresh token rotation
- Issue: long-lived refresh token (30d default) + short-lived access JWT (15min default — already in spec)
- On `POST /api/auth/refresh`: mark old refresh `revoked_at = NOW()` AND issue new pair
- Detection of reuse: if a `revoked_at` refresh is presented, REVOKE the entire chain (CHAIN_REVOKED audit event)

### Audit log wiring
Call `auditLog()` from every auth boundary:
- `auth.login.success` / `auth.login.failure`
- `auth.refresh.rotated` / `auth.refresh.chain_revoked`
- `auth.token.revoked` (current `/api/auth/revoke`)
- `auth.device.code_issued` / `auth.device.approved` / `auth.device.poll_pending`
- `auth.user.created` (first OAuth callback for a new user)
- `auth.invalid_token` (every 401 from `authenticateRequest`)

### MCP tool handler wiring
- MCP tools already read `claims.org` via `getSessionClaims` (Task 23.5). Phase 2 changes `claims.user_id` from `"legacy"` to a real `users.id` UUID. Audit events for MCP-invoked tools now have user-identity attribution.

## Phase 2 open design questions (for /brainstorm)

1. **Org membership model**: 1 user = 1 org (simple) vs N:M (real multi-tenant SaaS)? Phase 1 assumes 1:1 via `users.org_id` FK. Real SaaS needs a `user_orgs` join table. Decide before OAuth lands or it's a migration headache.

2. **GitHub-organization → coordinator-org mapping**: when a user authenticates via GitHub, what org do they belong to?
   - Option A: their GitHub username (e.g. `org_id = "github:swoofer"`)
   - Option B: first GitHub org they have admin access to
   - Option C: explicit selection at first login (multi-org users pick)
   - Option D: server-configured allowlist (only members of `COORDINATOR_GITHUB_ORG=foo` can sign in, get `org_id=foo`)

3. **JWT TTL strategy**: spec says 15min access + 30d refresh. Verify these still feel right after Phase 1 implementation showed real session patterns.

4. **PKCE storage**: where does the `code_verifier` live between authorize and callback? Options:
   - Session cookie (requires session middleware in coordinator — none today)
   - Server-side cache keyed by `state` (Redis? In-memory map?)
   - Encrypted in `state` itself (stateless but requires symmetric key)
   - In `device_auth_requests` table? (only for device flow)

5. **Device Flow UX**: the `device.approve` endpoint needs the browser-signed-in user to confirm. Where does that confirmation page live?
   - Coordinator dashboard route `/auth/device` (we already serve a dashboard)
   - Bare-bones HTML returned by coordinator itself
   - Redirect to a configured trusted UI

6. **Multi-IdP registration**: when can `registerProvider(new GoogleProvider(...))` get called? Phase 4 per the original spec, but Phase 2 should at least define the registration API so Phase 4 is mechanical.

7. **Refresh token storage**: refresh tokens are sensitive — store as bcrypt hash like passwords? Or accept that DB compromise = session compromise and store plaintext for revocation lookups? Spec doesn't address.

8. **Logout semantics**:
   - Local logout (revoke current refresh, leave others)
   - Global logout (revoke all refresh tokens for user)
   - Spec mentions Phase 2 logout but doesn't pick semantics

## Suggested process

1. **`/brainstorm` session**: load this file as context, get to a "yes I understand the trade-offs" answer on each open question above.
2. **Spec draft**: ~50KB design doc like `2026-05-11-auth-saas-ready-design.md`, focused on Phase 2 only.
3. **4-round multi-agent review** (matching Phase 1 process):
   - Round 1: 20 reviewer agents on the draft, surface ambiguities
   - Round 2: 20 reviewer agents on the revised draft
   - Round 3: 20 reviewer agents on the spec
   - Round 4: 20 reviewer agents on the final plan
4. **Implementation plan**: Phase-1-style task list with 20-40 tasks, each independently reviewable.
5. **subagent-driven-development execution** (the workflow that just shipped v0.7.0).

## When this file gets deleted

When the real Phase 2 spec lands. Until then it's the persistent roadmap memory + brainstorm seed.

## Why not write the full spec now

Same reason PR #19 was closed: speculative spec writing without a driving use-case (specific client, specific deployment) ages poorly. Better to:
- Ship `mcp-coordinator@0.7.0` to npm (done)
- Get feedback from at least one real Phase 1 deployment
- Use that feedback to constrain Phase 2 spec choices
- Write the spec when at least one open question above gets answered by external pressure

The Phase 1 hooks are durable enough that this delay costs near-zero — adding OAuth on top of the existing `IdPProvider` empty registry and `users`/`refresh_tokens` tables is pure feature work, not architectural.
